# 评审与改稿

## 评审

可以直接评已有稿，不要求完成本 skill 的准备、素材、叙事模块。先识别待评对象、版本、听众、目标及使用方式；从当前任务文件或用户话里承接，必要时补问。评他人稿时使用对方上下文，不套用评审者自己的身份与目标。

正式交接建议新开对话，以减少原写作上下文干扰；这是使用建议，不是日常自评的硬门槛，也不意味着已取得独立真人验证。

普通评审直接开始。仅当用户要求压力评审时，读取用户给出的听众临时状态，如“只有三分钟，注意力容易分散”。用户没给具体状态时问这一项，或改做普通评审；不自行编造听众状态。压力评审不替换原稿角色，不改变事实标准。

按实际可核查范围检查：结论是否清楚、支撑是否成立、顺序是否适合对象、希望对方理解或判断什么是否明确。材料不全时可以先做有限评审，显式标“未核原始数据”；不把缺附件直接说成作者造假。

保存 `04-评审/评审意见.md`：

- 待评稿件、版本、任务上下文、实际读取的材料与核查范围。
- 最值得保留的内容。
- 本轮优先处理的问题，通常不超过三个；更多问题只有用户要完整审查时再展开。
- 每项：页码和原句 → 具体问题及后果 → 证据问题／表达问题／待核实疑问 → 最小修改建议或需要作者回答的问题。

再次评审时写在同一文件，新一轮放最前，标“第 N 轮”、评审对象的版本或更新时间；逐条说明上一轮问题已解决、部分解决还是仍在。旧轮次保留，不覆盖。

“逻辑不好”“不够高级”不算可执行意见。先核对原文是否已有解释或限制，不截取半句制造问题。评审交付可记已完成，不要求作者同意所有建议；这不等于原稿已确认。

## 改稿

用户说 `/改稿` 并给出范围时，按范围修改；说“按这份意见改”可处理其中明确、可执行的项，不逐项重复索要许可。遇到互斥建议、需要新事实或改变目标时，只问该关键分歧，其余部分继续。

直接编辑 project 中对应的 Markdown。局部改写更新原文件；涉及整稿重写或覆盖已交付稿时，先将该重要稿件另存至 `归档/`，不为每轮小改生成快照。在 `04-评审/修改说明.md` 写：依据哪份意见、改了什么、未采纳或仍待确认的项及理由。每次改稿追加一节并注明日期，不覆盖之前的记录。同步受影响的讲稿和交接；评审针对旧内容的结论标需复核。

没有改稿请求时，评审到意见为止。不要自动润色整稿、发送给作者或替用户采纳建议。
